# Final Project — Demo & Code

**GroupRide is a solo project by Derick Lee.** Partner registration and partner collaborator setup are inapplicable. Put Derick Lee’s full name on the demo booking.

## Project and team

- Choose a project you care about and would enjoy demonstrating. Scope it for about two weeks of building and testing.
- Build working software. The app may call a model at runtime, and your own code must do most of the work. A model behavior study, a collection of prompts, or a thin layer over a model or an existing app does not meet the software requirement. The demo and code grade evaluates the software you build.
- Originality is optional. You can reuse an existing codebase or libraries from outside the course homework. Link the sources and explain what you reused, changed, and built.
- Work solo or in a pair of at most two students. To register a pair, both partners submit each other’s UT EID through the **Final project partner request** assignment.
- Read the **Final project guide** in the Homework section of the course site’s slide catalog. Make a copy of the Google Slides writeup template and prepare the companion [Writeup PDF](WRITEUP.md).

## Repository and reproducibility

- [ ] Create or fork one GitHub repository per team under a student’s own account. Add your partner as a collaborator if applicable. Public repositories are allowed. Grant the instructor and TA access to a private repository before submitting its URL.
- [ ] Keep course homework material out of the project, the repository, and its Git history. This includes starter code, solutions (including your own), tests, data, and handouts.
- [ ] Put setup, demo, and validation commands, required versions, and configuration in the [repository README](../README.md). Keep cited tests, inputs, and results with the code.
- [ ] Provide fixtures, a mock, or a replay for external services so staff can run the core workflow without private credentials, paid services, or production data. Rehearse from a clean start. GroupRide’s fictional-address walkthrough is documented in the [invitation demo instructions](../README.md#run-the-invitation-demo).

## Live demonstration

- [x] Book **one slot per team**, about **20 minutes**, on the demo sign-up sheet. Include every teammate’s full name. The instructor and TA attend all demos. Derick Lee confirmed the solo booking.
- [ ] Run the core workflow from known data and show its result.
- [ ] Show a test that could catch a wrong result. Explain how you established the expected result.
- [ ] Explain two design or evaluation decisions, including the alternatives, evidence, what you did next, and the agent’s role where relevant.
- [ ] Tell a debugging story that covers the symptom, how you narrowed down the cause, what changed, and how you checked the fix.
- [ ] Explain what you contributed, the major components, and one concrete case the project cannot handle. Both partners should be able to explain their work.
- [ ] Use the same slides as the writeup to introduce the working project, explain decisions, and answer questions. Present slides in the order that best supports the demo.

## Submission and grading

- [ ] Submit the **GitHub repository URL** to **Demo & Code** by the due date shown in Canvas. Submit the slide PDF to the separate **Writeup** assignment by the same due date.
- [ ] Check the Canvas **available until** date. You can improve the repository and resubmit the slide PDF until that edit close. Add any extra result or clarification requested during the demo by then.

The grading evidence is the live demonstration, the submitted repository’s default branch at edit close, and the last slide PDF submitted by that time. The slide deck serves as the writeup. There is no separate written or Markdown report to submit.
